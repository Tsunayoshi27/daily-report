# 阶段评审单 — design.md 红队评审

> 评审对象：specs/design.md v1.0 | 评审日期：2026-11-09 | 红队角色：AI | 评审模式：生成—评审

---

## 评审方法说明

根据课程指导书第二周要求，采用"生成—评审"双轨模式：AI 以红队身份对 design.md 逐条审查，挑出架构缺陷、规范矛盾、范围缺失、逻辑漏洞；设计者逐条回应"接受并修复 / 反驳并说明理由 / 标记延期至下版本"。最终评审单与 design.md 一同提交。

## 三、接口契约问题

| 编号 | 审查项 | 问题描述 | 建议修复方案 | 响应 | 修复状态 |
|:---:|--------|----------|-------------|:---:|:---:|
| I1 | 采集接口签名与约束矛盾 | `collect_github(token, repos, date)` 和 `collect_feishu(app_id, app_secret, date)` 入参含凭证，但"行为约束"写"凭证仅从环境变量读取"——到底传参还是读环境变量？ | 统一：接口签名改为 `collect_github(repos, date)`，token 在 `__init__` 中从环境变量读取 | | |
| I2 | FileExporter 签名与抽象类不兼容 | Pusher 基类 `push(report) -> bool`，但 FileExporter 的签名是 `export(report, format, output_dir) -> Path`，无法多态调用。 | 改为 `push(report, **kwargs) -> bool`，format 和 output_dir 在 `__init__` 中配置 | | |
| I3 | filter_content 无法传警告 | "空话占比 > 30% 时标记警告"——返回值是 `str`，警告无处传递。 | 改为返回 `tuple[str, list[str]]` 或使用日志 warn 级别输出 | | |
| I4 | main() 返回值风格不 Pythonic | `main() -> int` 返回 0/1 是 C 风格，Python 主流程应返回 `Optional[DailyReport]` 或抛异常。 | 改为 `main() -> DailyReport`，异常情况 raise 而非返回 int | | |

## 四、数据模型缺陷

| 编号 | 审查项 | 问题描述 | 建议修复方案 | 响应 | 修复状态 |
|:---:|--------|----------|-------------|:---:|:---:|
| D1 | RawRecord 缺完成状态字段 | "识别未完成项归入明日计划"——但 RawRecord 无 `status` / `is_completed` 字段，Assembler 无法判断。 | 新增 `status: str` 字段，枚举 `done` / `pending` / `blocked` | | |
| D2 | DailyReport 字段冗余 | `today_done` + `tomorrow_plan` + `risks` 三个分段字段 + `ai_draft` 全文 + `final_content` 全文——同一日报存三份，修改时需保持三者一致。 | 保留分字段（便于结构化查询），去掉 `ai_draft`；或保留 `ai_draft` 为唯一内容字段，分字段改为视图/属性 | | |
| D3 | is_submitted 缺少 CHECK 约束 | SQL `is_submitted INTEGER DEFAULT 0` 没有 CHECK，可写入 2/-1/99 等非法值。 | 加 `CHECK(is_submitted IN (0,1))` | | |

## 评审结论

| 维度 | 评分 | 说明 |
|------|:--:|------|
| 四层架构图 | 7/10 | 结构清晰但缺少 AI 模块、缺少管理端 |
| 模块职责 | 5/10 | 缺核心 AI 生成模块，管理端模块完全缺位 |
| 数据模型 | 6/10 | 实体完整但字段冗余、缺状态字段 |
| 接口契约 | 5/10 | 签名矛盾、返回值设计不合理 |
| ADR | 5/10 | 缺最关键的 2 份（AI 选型、配置管理） |
| 非功能约束 | 6/10 | 框架有但实现细节不足 |
| proposal 覆盖率 | 4/10 | 11 项仅覆盖 4 项 |

**总评：design.md v1.0 不通过。** 两大致命缺陷——缺少 AI 内容生成模块、proposal 范围覆盖率仅 36%——必须在 v1.1 中修复。建议按 R1→R2→I1→I2→D1→ADR1→ADR2→N2 的优先级逐条修复后重新提交评审。
